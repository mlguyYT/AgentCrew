# Acceptance Criteria Checklist

## Purpose

Use this checklist before implementation when a request needs clearer scope or validation points.

---

## Checklist

- [ ] requested outcome is stated in one sentence
- [ ] intended user or operator impact is clear
- [ ] in-scope behavior is listed
- [ ] out-of-scope behavior is listed
- [ ] criteria are observable and testable
- [ ] error, empty, permission, and compatibility behavior are covered when relevant
- [ ] preserved behavior is called out for refactors
- [ ] validation or test evidence is identified
- [ ] reviewer, specialist, and human decision gates are listed when triggered
- [ ] open questions are blockers only

---

## Human Decision Trigger

Ask the human before implementation when acceptance criteria require choosing between materially different product outcomes, accepting risk, changing public behavior, accepting migration/data-loss risk, or overriding a quality gate.
